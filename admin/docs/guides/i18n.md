# i18n & RTL — next-intl

The product ships in both directions. A direction bug is a layout bug.

## Structure

- Locale segment: `src/app/[locale]/…` with messages in
  `messages/en.json` and `messages/ar.json` (established by the first
  i18n task; every later feature follows it).
- Locale config in `src/lib/i18n/`: `locales`, `defaultLocale`,
  `getDirection`.
- `<html lang={locale} dir={direction}>` is set in the root layout from
  the locale — nowhere else in the tree.
- Locale detection/redirects run as a guard in the proxy chain
  (auth.md).

## Hard rules

- Zero hardcoded user-facing strings — every visible string goes
  through `t()`. Message keys are namespaced by feature:
  `users.table.empty`.
- A new message key lands in BOTH locale files in the same commit. A
  key existing in one locale only is a defect.
- Logical properties ONLY: `ps-` `pe-` `ms-` `me-` `start-` `end-`
  `text-start` `text-end` `rounded-s-` `rounded-e-`. The physical pairs
  (`pl-`/`pr-`, `ml-`/`mr-`, `left-`/`right-`, `text-left`/`text-right`)
  and the `rtl:`/`ltr:` variants are forbidden — one class must serve
  both directions.
- Single exception: direction-implying icons (arrows, chevrons) flip
  with `rtl:rotate-180` on the icon element itself. No other `rtl:`
  usage exists.
- Dates, numbers, currencies, and relative time go through next-intl
  formatters (`Intl` underneath). Manual formatting or hand-built
  locale strings are forbidden.
- Never branch component logic on the locale value for layout — if a
  component needs `if (locale === "ar")` to render correctly, the
  styling is wrong; fix it with logical properties.
